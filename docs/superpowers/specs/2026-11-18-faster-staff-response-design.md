# スタッフ操作の応答速度改善 設計書(小変更)

日付:2026-11-18 / 親設計:`2026-11-17-mogiten-order-design.md`

## 目的
スタッフ画面でボタンを押してから画面が変わるまでが遅い。原因は2つ。
- 通信経路:Vercel 関数が既定の米国東部、Supabase がムンバイ。1回の操作で太平洋とインド洋を何度も往復している。
- 画面の更新待ち:操作の応答と、注文一覧の再取得を待ってから画面を変えている。

## 検討した案
- **① Supabase を東京に作り直し、Vercel 関数も東京 `hnd1` にする**(採用。ユーザー決定):往復がすべて国内になる。お客さんのスマホの通信も速くなる。
- ② Vercel 関数をムンバイ `bom1` にする:手間は最小。ただし日本↔ムンバイの往復が残るため不採用。
- **B. 楽観的更新**(採用):押した瞬間に画面を変え、失敗したときだけ取り直す。
- C. 操作の応答で一覧も返す:A+B があれば効果が小さいので見送り。

## 決定事項
- `vercel.json` に `{"regions": ["hnd1"]}` を書く。
- README:Supabase のリージョンは Northeast Asia (Tokyo) と明記する。Supabase の引っ越し手順を追記する。
- 楽観的更新(スタッフ画面):
  - complete:調理中 → 受け取り待ち(readyAt = 今。受け取り待ち列は番号順)
  - deliver / cancel:その注文を消す
  - revert:受け取り待ち → 調理中(番号順の位置へ。readyAt = null)
  - 売り切れ切り替え:該当品の isSoldOut を反転する
  - 失敗したら一覧を取り直し、トーストを出す(409 なら「他の端末で先に操作されました」、それ以外は「操作できませんでした。もう一度お試しください」)
  - 楽観的更新の時点で、それ以前に始まった一覧の取得結果は捨てる(`latestOnly` に `invalidate()` を追加)
- 状態の変換は純粋関数として `src/lib/staff/optimistic.ts` に置き、テストする。
- ユーザー作業:東京の Supabase を新設し、SQL を 0001〜0004 と storage.sql の順に実行、Vercel の環境変数3つを差し替えて Redeploy、メニューを再登録、ムンバイのプロジェクトを削除。
