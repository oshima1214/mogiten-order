# メニューの完全削除と注文データの削除 設計書(小変更)

日付:2026-11-18 / 親設計:`2026-11-17-mogiten-order-design.md`

## 目的
注文が付いたメニューは削除できず「非表示」になるだけで、管理画面に残り続けた。リハーサルの試し注文も集計と番号に残る。メニューを本当に削除でき、注文データをまとめて消せるようにする。

## 検討した案(ユーザーが A+B を選択)
- **A. メニューを本当に削除**:`order_items.menu_item_id` の外部キーを `on delete set null` にする。明細は注文時点の商品名・金券枚数を持つので、表示と集計は壊れない。
- **B. 注文データの削除**:管理画面から全注文・明細・採番を削除する。
- (不採用)非表示品を一覧から隠すだけ:根本的に消せないままなので不採用。

## 決定事項
- **A**
  - 削除ボタンは注文の有無に関係なく削除し、写真も消す。「非表示」ボタンは残す。
  - 注文内容の並びは、メニューの表示順に従う。削除済みの品は末尾に並べ、末尾どうしは名前順。
  - 確認文言:「「◯◯」を削除しますか?売上の記録は残ります」
  - 「注文履歴があるため非表示にしました」というメッセージは廃止する。
- **B**(範囲はすべての注文。Claude の判断)
  - メニュー管理画面の最下部に「注文データの削除」欄を置く。「削除」と入力したときだけボタンが有効になる。
  - 消すもの:`orders`, `order_items`, `order_counters`。消さないもの:メニュー・写真・店名・設定。
  - 削除後は番号が 1 から振り直され、集計は 0 になる。お客さんのスマホは次の更新でメニューに戻る(トークンが見つからないため)。
  - 実行は service_role 専用の DB 関数 `admin_reset_orders()` で行う。API は `POST /api/admin/orders/reset`(スタッフ認証必須、body `{ confirm: "削除" }`)。
- **本番反映**:変更は新しいマイグレーション `supabase/migrations/0004_menu_delete_and_order_reset.sql` に入れる。実行済みの 0001〜0003 は変更しない。README に適用手順を追記する。
