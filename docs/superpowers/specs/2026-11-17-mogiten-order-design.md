# 模擬店 注文・呼び出しシステム 設計書

日付:2026-11-17
画面見本:https://claude.ai/artifact/LyGx1X5NZyCkWG8vuNRA3W(お客さん3画面・スタッフ画面・売上集計)

## 1. 目的と背景

学園祭の模擬店で使う Web アプリ。お客さんが自分のスマホで注文し、できあがったことを自分のスマホで確認できるようにする。

- 番号札や QR 付きレシートなど、注文ごとの紙の準備をしたくない → 店頭に QR ポスター1枚だけ貼る
- 支払いは金券のみ。お金のやり取りはシステムの外(受け取り時に金券を渡す)

## 2. 目標 / やらないこと / 失敗の条件

**目標**
- お客さんが QR → メニュー → 注文 まで迷わずできる
- お客さんは自分の番号・状態・前の待ち組数を見られる
- スタッフは1枚の画面で 注文確認 → 完成 → 受け渡し を回せる
- 品目ごとの販売数と金券枚数を集計できる

**やらないこと(非目標)**
- 支払い・決済機能
- プッシュ通知・LINE・SMS・音やバイブでの呼び出し(お客さんが自分でページを開いて確認する)
- iPhone のホーム画面追加(PWA)対応
- いたずら注文対策、スタッフによる代理入力(全員スマホを持ち操作できる前提)
- 待ち時間の目安表示
- 複数の模擬店の同時運用(1店舗専用)

**失敗の条件(動いても失敗とみなすもの)**
- 当日、スタッフ画面に注文が届かない/遅れる、状態がお客さん画面に反映されない
- お客さんがタブを閉じたら自分の注文に戻れない
- 同じ番号が2つの注文に振られる

## 3. 前提・制約

- 利用者:お客さん(スマホ、iPhone/Android のブラウザ)、スタッフ(タブレットまたはノート PC 1台)
- 費用は無料枠の範囲で運用する
- 当日にサーバーを手で動かし続ける運用はしない
- 見た目は Apple 風(画面見本のとおり)。細部は実装後にまとめて調整する

## 4. 検討した作り方(Approaches)

GitHub 上の文化祭向け OSS を調査して比較した。

| 方式 | 参考 | 評価 |
|---|---|---|
| Firebase Firestore + Next.js | Hazakura2024/festival-ticket | お客さん画面の作り(状態が変わると全面の色が変わる、localStorage で本人識別)が近い。集計は弱い |
| **Supabase(PostgreSQL + Realtime)+ Next.js** | luxenjade/3-1-yakitori、dorasei1224/school-festival-pos-ver-2 | 注文・状態・集計を SQL で素直に扱える。レジ/厨房/受け渡し画面の分け方が近い |
| 自前サーバー + WebSocket | kawaemon/krs-pos(MIT) | 当日サーバーを動かし続ける必要があり不向き |

**採用:Supabase + Next.js、Vercel で公開**(Claude の提案。ユーザーは画面見本を承認し、作り方の変更は求めていない)。
**役割分担**
- **Next.js**:画面(お客さん・スタッフ・集計・管理)と、合言葉チェックなどのサーバー側処理(Route Handler / Server Action)
- **Vercel**:Next.js アプリの公開(無料枠)。GitHub に push すると自動で更新
- **Supabase**:データベース(PostgreSQL)、変更の即時配信(Realtime)、写真の保存(Storage)。番号の採番や「前に N 組」の計算は DB 関数で行う
- お客さんのブラウザは Supabase の公開キーで、許可された操作(メニュー閲覧・注文作成・自分の注文の閲覧/取消・Realtime 購読)だけを直接行う。スタッフ操作は Next.js のサーバー側で合言葉を確認したうえで、秘密キーを使って Supabase を操作する。秘密キーはブラウザに渡さない

**公開先は Vercel(ユーザー決定)**。Cloudflare Workers も検討したが、Next.js をそのまま動かせる Vercel を選んだ。Vercel の無料(Hobby)プランは非営利の個人利用が条件のため、利用前に規約を確認する。

**複数店舗で使う場合(ユーザー決定)**:アプリは1店舗用のまま。コードは GitHub の1リポジトリにまとめ、店舗ごとに Vercel のプロジェクトを1つ追加し、その店舗のメンバーが自分で作った Supabase プロジェクトに環境変数でつなぐ。1人が無料枠を増やす目的でアカウントを複数作ることはしない。

注:参考 OSS のうちライセンスが明示されているのは krs-pos のみ。他はコードを流用せず、考え方だけ参考にする。

お客さんの注文方法も検討した:
- スタッフが口頭注文を入力 + 番号札(事前印刷 QR)→ 番号札の準備が不要な方がよいため不採用
- **お客さんがセルフ注文** → 採用(ユーザー決定)

## 5. 決まっていること(ユーザー決定)

### お客さん側の流れ
1. 店頭の QR ポスター(全員共通の1つの URL)を読み、メニューを開く
2. 品目と数量を選んで「注文する」
3. 待機画面:番号、状態(調理中)、「あなたの前に N 組」、注文内容、金券の合計枚数、「注文を取り消す」ボタン
4. 開いている間は自動更新(更新ボタン不要)。タブを閉じても同じ URL を開けば自分の注文に戻れる(ログイン不要、ブラウザに記録)
5. 完成すると「できました」画面(全面の色が変わり、番号と金券枚数を大きく表示)。音・バイブ・通知はなし
6. 受け取り時に金券を渡す

### スタッフ画面(1枚)
- ヘッダー:調理中の組数、受け取り待ちの組数、売上集計ページへのリンク
- 「作る数の合計」:調理中の注文に含まれる品目の合計数
- 左:調理中(古い順)。番号・品目・注文時刻・経過時間。「完成」「取消」。時間がたった注文は目立たせる
- 右:受け取り待ち。「受渡済」「調理中に戻す」「取消」。受渡済を押すと消える
- 下:品目ごとの 販売中/売り切れ 切り替え。売り切れはお客さんのメニューで選べなくなる
- 新しい注文はリロードなしで追加される

### 売上集計ページ(別ページ・必要)
- 受け取り済みの金券枚数、受け渡した注文件数、取り消し件数
- 品目ごとの販売数と金券枚数
- 数えるのは「受渡済」の注文のみ

### 管理画面(ユーザー決定:作る)
- メニューの追加・編集・削除をアプリ内で行う(Supabase の管理画面は使わない)
- スタッフ画面と同じ合言葉で入る

## 6. Claude が決めたこと(違えば修正)

- **値段の単位**:品目ごとに「金券 N 枚」で持つ。円は扱わない
- **管理画面の項目**:品目名、金券枚数、表示順(上下移動)、写真(任意。Supabase Storage に保存)、メニューに表示する/しない、売り切れ。あわせて店名(お客さん画面の上部に表示)も設定できる。注文が付いた品目は削除せず「表示しない」にする(集計を壊さないため)
- **売り切れ切り替え**:管理画面に加え、スタッフ画面の下部からもすぐ切り替えられる
- **営業日**:注文に営業日(日付)を持たせ、番号は日ごとに 1 から振り直す。集計は「日付ごと」と「合計」を切り替え
- **番号の採番**:DB 側で日ごとの連番を原子的に振る(重複させない)
- **お客さんの識別**:注文作成時に推測できないトークンを発行し、ブラウザの localStorage に保存。待機画面はトークンで自分の注文を読む。注文が「受渡済/取消」になったら、次に開いたときはメニューに戻る
- **お客さんの取り消し**:調理中の間だけ可能。完成後はスタッフのみ取り消せる
- **数量の上限**:1品目あたり 1 注文 10 個まで
- **「前に N 組」**:自分より前に作られた、同じ営業日の「調理中」の注文数。完成した注文は数えない
- **スタッフ画面の保護**:スタッフ用の合言葉(パスコード)でログインする簡易方式。合言葉は環境変数で設定
- **権限**:お客さんは「注文の作成」「自分の注文の閲覧・取り消し」「待ち組数の取得」「メニューの閲覧」のみ。それ以外の操作はスタッフ認証が必要(Supabase の RLS と DB 関数で制御)
- **リアルタイム更新**:注文・メニューが変わると DB トリガーが Supabase Realtime の公開ブロードキャストに「変わった」という合図だけを送り(中身は含めない)、各画面はそれを受けて自分に許された経路で再取得する。切断時に備えて定期再取得も併用(お客さん 15 秒、スタッフ 10 秒)。お客さんに注文テーブルの読み取り権限を与えずに済むため
- **「時間がたった注文」**:10 分以上で強調表示
- **状態**:`cooking`(調理中)→ `ready`(受け取り待ち)→ `delivered`(受渡済)、どこからでも `cancelled`(取消)。`ready` → `cooking` へ戻せる
- **言語・端末**:日本語のみ。お客さん画面はスマホ縦、スタッフ画面はタブレット横を主に想定し、他のサイズでも崩れないようにする

## 7. 実装者に任せること

- Next.js のルーティング構成、コンポーネント分割
- テーブル・関数の具体的な定義(上の決定を満たすこと)
- スタイルの実装方法(画面見本の見た目に合わせる)
- テストの範囲と方法
- デプロイ手順書(Supabase プロジェクト作成、環境変数、Vercel 公開、QR ポスターの作り方)。次の2点を必ず含める:
  - 店舗を追加する手順(Supabase プロジェクト作成 → スキーマ適用 → Vercel プロジェクト追加 → 環境変数設定)
  - Supabase の無料プロジェクトは1週間使われないと停止するため、学園祭の数日前に起動と動作を確認すること
